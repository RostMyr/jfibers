# HTTP load comparison

This is a bounded, closed-loop client workload against an isolated loopback HTTP
server. It complements the tiny task and waiting benchmarks in [README.md](README.md).
It measures HTTP orchestration, including transport and response validation.

## Reproduce

Requires the project's JDK/Maven versions and Python 3 on Linux:

```sh
./mvnw -Pbenchmarks -pl jfibers-benchmarks -am clean verify
python3 jfibers-benchmarks/http_run.py --quick
python3 jfibers-benchmarks/http_run.py --profiles --output jfibers-benchmarks/target/my-http-run
python3 jfibers-benchmarks/http_summarize.py jfibers-benchmarks/target/my-http-run
```

Use a new output directory. The runner never overwrites a previous dataset.
`--quick` validates the protocol, byte counts, generated bytecode and shutdown;
its timings are not performance evidence. The full run uses 36 fresh client/server
JVM pairs (about 16 minutes); optional profiling adds three separate pairs. Avoid concurrent builds,
tests or other workloads while collecting data.

## Equal work and concurrency

Each client flow repeatedly performs one operation:

1. GET `/first`, read and validate status 200 and all 1,024 response bytes.
2. Compute the body's checksum and send it in GET `/second?token=...`.
3. Read and validate the second response's status and all 1,024 bytes.

The server rejects an incorrect token. It optionally sleeps for 5 ms **per request**;
an operation therefore has at least about 10 ms of deliberate waiting in that
scenario. Results report operations/second; HTTP requests/second is twice that
number. Client and server independently count requests and body bytes. Any error,
timeout, zero-success run or accounting mismatch fails the runner, preserving
available raw results.

| Backend | Persistent client flow |
| --- | --- |
| jfibers | One build-time-instrumented fiber per flow; `Fiber.call(HttpClient.sendAsync(...))` at each request |
| Virtual threads | One virtual thread per flow; ordinary `HttpClient.send(...)` at each request |
| CompletableFuture | `sendAsync(...).thenCompose(...).thenAccept(...)`; a small trampoline prevents recursive immediate completions |

All backends use JDK HttpClient, HTTP/1.1, connection reuse, the same byte-array
body handler, a four-thread client executor, four common-pool workers and four
virtual-thread carriers. A jfibers manager executes fiber bodies on one thread.
Flows persist throughout a phase: this is **not** a benchmark of creating one task
per incoming server request. Each flow has at most one HTTP request outstanding;
there is no unbounded submission queue or artificial batching barrier.

The server is a separate JVM using JDK HttpServer and a virtual-thread executor.
It binds only to `127.0.0.1` on an ephemeral port. TCP_NODELAY is enabled to avoid
an HTTP header/body split interacting with delayed TCP acknowledgements. No
Internet endpoint is contacted by the test. Both JVMs share the host CPU quota;
separate processes separate CPU accounting, not physical resources.

## Measurement protocol

The full matrix is concurrency 32/256 × server delay 0/5 ms × three backends ×
three independent repetitions. Both scenario and backend order rotate between
repetitions. Each pair warms up for 15 seconds, drains all operations, then runs a
10-second measurement. The client performs an explicit GC after warmup, outside
measurement, while retaining warm connections and compiled code.

Admission stops at the phase deadline. Already-started operations finish and
remain in both latency and throughput accounting. Throughput divides successful
operations by elapsed time **including drain**, avoiding end-of-window censoring.
Each request has a 5-second timeout; the Python supervisor also bounds process
startup, phases and shutdown. The result includes drain duration and per-second
completion counts, allowing startup/JIT/GC effects to be inspected. A preliminary
5-second warmup showed continued throughput growth early in the measurement at
concurrency 256; its timings were excluded, and the final protocol uses 15 seconds.

Latency spans both HTTP requests, validation and scheduling delays within a flow.
Thread-confined histograms use 64 subdivisions per power of two in microseconds;
percentiles are upper bucket bounds (up to 1.563% quantization plus rounding to
microseconds). They include failed operations if any. The summary reports medians
and min/max ranges across independent JVMs, including the median of each JVM's
p95/p99; it does not pool percentiles or claim a statistical confidence interval.

This is a **closed-loop** load test. Slower completions reduce offered load, and
there is no external arrival queue. Percentiles do not estimate overload behavior
under a fixed open-loop arrival rate; no coordinated-omission correction is applied.

Process CPU comes from the JVM's process counter. Client and server CPU are
reported separately in average occupied cores, with raw snapshots retained. They
include JIT, GC and transport work. Server CPU spans the control handshake around
the phase; client CPU spans the phase itself. The runner also records cgroup
throttling counters, VM/Java details, exact commands, source hashes and JAR hash.

Client heap is sampled every 100 ms with MemoryMXBean: mean, observed peak, before
and after, plus GC count/time. Client heap is fixed at 512 MiB and server heap at
256 MiB, both using G1. Sampled used heap includes floating garbage, HTTP buffers,
connections, futures and fixed per-flow histograms (about 16 KiB each). It is not
retained memory per fiber, RSS or an allocation-rate measurement. Short peaks can
fall between samples; use the separate waiting probe for retained-task estimates.

## Separate profiling

`--profiles` repeats the concurrency-256, 5-ms scenario once per backend with JFR's
`profile` configuration enabled only around the measured phase. These trials are
stored in `profiles.json` and excluded from `http.json` and the comparison summary.
JFR overhead is not mixed into the performance results.

The runner retains local `.jfr` files and extracts execution/native sample counts,
top sampled leaf methods/stacks and overlapping inclusive categories using `jfr print`.
Sample categories are not exclusive and do not sum to 100%. CPU samples are
statistical evidence of where execution was observed, not exact subsystem costs;
native selector waits can appear in samples, so execution and native samples are
reported separately. Short recordings and inlining limit resolution. Thread-park,
monitor and GC event counts provide additional context. Object-allocation samples
are aggregated by their estimated byte weight, not treated as exact allocation totals.

Binary recordings are ignored by Git; reproducible commands, recording hashes
and extracted stack summaries are committed with results. To inspect a local
recording in detail:

```sh
jfr summary path/to/profile.jfr
jfr view hot-methods path/to/profile.jfr
jfr view allocation-by-site path/to/profile.jfr
```

The test does not cover TLS, HTTP/2, WAN latency, JSON/business-heavy processing,
framework request handling, JDBC, mixed blocking libraries, task cancellation or
an open-loop overload/SLO test. Those require separate workload decisions.

## Recorded results: 10 October 2026

Revision `223880c`, Temurin 27+35, Linux x86-64, AMD EPYC 9V74 VM with a shared
four-core CPU quota. The complete dataset is in
[results/2026-10-10-http](results/2026-10-10-http): `environment.json`, `http.json`
and `profiles.json`. Source, JAR and recording hashes were verified after the run.
`summary.md` retains the full comparison with ranges; `*-thread-cpu.txt` retains
the standard JFR thread CPU views and their extraction commands.
All 36 unprofiled measurements and three separate profiles completed. The
unprofiled measurements validated **6,269,736 operations / 12,539,472 HTTP requests**
with zero client errors, timeouts, server errors or byte-count mismatches.

At 32 flows with the same delay, median client CPU is 0.46, 0.46 and 0.45 cores,
respectively. Sampled used heap is broadly similar; it does not demonstrate the
large retained-task memory advantage of the separate 10,000-waiter microbenchmark.

here, and this measurement cannot isolate retained fiber or virtual-thread memory.

by 89,231,714 over the whole run, including warmup and profiling. The latter is a
cgroup counter, not a request-latency or wall-time correction. Client and server
compete for the shared quota, especially with zero server delay. Per-second rates
still fluctuate after warmup; the ranges and the machine configuration matter.
These short, local runs do not establish portable throughput rankings or SLOs.

### What the profiles show

The separate 10-second JFR recordings contain the following **Java execution
samples with stacks**, excluding native-method samples:

| Backend | Execution samples | Samples with a JDK HTTP frame | Samples with a jfibers runtime frame |
| --- | ---: | ---: | ---: |
| jfibers | 711 | 642 (90.3%) | 42 (5.9%) |
| Virtual threads | 526 | 458 (87.1%) | 0 |
| CompletableFuture | 581 | 512 (88.1%) | 0 |

Categories overlap: a runtime frame may contain downstream HTTP work. These are
inclusive sampled stacks, **not percentages of total process CPU or an isolated
cost of FiberManager**. They also omit native VM/JIT/GC CPU. In the jfibers recording,
38 samples contain the compiled HTTP workload. Frequently sampled methods include
JDK HTTP's `SequentialScheduler.runOrSchedule`, completion processing,
`AbstractQueuedSynchronizer.signalNext` and selector/connection-pool work.
Weighted allocation samples are led by byte arrays, HTTP `MinimalFuture` objects,
object arrays and strings. Native selector waits are kept in a separate category.
The standard JFR data is sufficient to identify these areas without a new agent.

There is also a meaningful API difference inside this JDK: `HttpClient.send()`
starts exchange work inline until asynchronous I/O is necessary, whereas public
`sendAsync()` explicitly dispatches exchange work and, when pending, forwards
completion through the default CompletableFuture executor. This is documented
in the bundled JDK source, `HttpClientImpl.sendAsync` (the `exchangeExecutor`
overload). The test intentionally compares idiomatic application usage; it does
not isolate the scheduling primitive from these HTTP API costs.

### Implications and next experiment

jfibers delivers 2.9–15.1% fewer operations per second than virtual threads when
comparing the four scenario medians. With 256 flows and 5 ms per request, the gap
is 6.5%, and median p99 is 29.18 versus 23.04 ms. Its previous ready-future batch
advantage does not translate into an HTTP throughput advantage in this workload.
Virtual threads are the stronger default for this kind of ordinary blocking Java
application; this says little about custom cooperative scheduling or other I/O APIs.

The next useful control is **virtual threads awaiting `sendAsync(...).get()`**,
keeping the same transport/completion path as jfibers and CompletableFuture.
That can separate the HTTP API's dispatch cost from the scheduler comparison.
Follow it with a fixed-arrival-rate test that includes admission delay, bounded
queues, rejection, timeouts and cancellation in its latency/error accounting.
The current profiles do not justify assuming the single fiber owner is saturated
or rewriting the scheduler; parallel-manager experiments can follow evidence from
those controls. Re-run the relevant workloads after any resulting optimization.
